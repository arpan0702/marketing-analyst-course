Beginner

What a database actually is

You already understand this — you learned it in Module 1. A database table is just an Excel sheet with stricter rules: every column has one fixed type of data (numbers stay numbers, text stays text), and every row represents exactly one real-world thing. A database is simply a collection of these sheets ("tables") that can be connected to each other.

anatomy of a table

Your first query: SELECT

Every SQL question starts with the word SELECT. The simplest possible query asks for everything in a table:

SELECT * FROM orders;

Read it left to right, literally: SELECT (give me) * (every column) FROM orders (from the orders table). The * means "all columns." The semicolon just marks the end of the statement.

Usually you don't want every column — just the ones relevant to your question. Name them, comma-separated, instead of *:

SELECT channel, revenue FROM orders;

Filtering rows: WHERE

WHERE keeps only the rows matching a condition — the SQL equivalent of an Excel filter. It goes after the table name:

SELECT * FROM orders WHERE channel = 'Email';

Sorting and limiting: ORDER BY, LIMIT

ORDER BY sorts your result (ASC = ascending, low→high, the default; DESC = descending, high→low). LIMIT caps how many rows come back — essential once a table has thousands of rows.

SELECT * FROM orders ORDER BY revenue DESC LIMIT 5;

This reads as: "give me every column, sorted by revenue from highest to lowest, but only the top 5 rows."

Renaming a column: aliases (AS)

AS gives a column (or a calculated value) a cleaner name in your output — purely cosmetic, doesn't change the data.

SELECT channel, revenue AS order_value FROM orders;

Aggregating data: turning many rows into one number

These five functions collapse a column of many rows into a single summary number — this is the exact operation a pivot table's "Values" area does, just with a keyword instead of a drag-and-drop:

FunctionDoes
COUNT(*)how many rows
SUM(column)total
AVG(column)average
MIN(column) / MAX(column)smallest / largest value

Grouping rows: GROUP BY

On its own, SUM(revenue) collapses the entire table into one number. GROUP BY tells it to collapse per category instead — one summary row per channel, per month, per whatever you group by.

SELECT channel, COUNT(*) AS num_orders, AVG(revenue) AS avg_revenue
FROM orders
GROUP BY channel;

mental model bridge

PIVOT TABLE (Module 1)                SQL EQUIVALENT

Filtering groups: HAVING vs. WHERE

This trips up almost everyone once: WHERE filters individual rows before grouping happens. HAVING filters the grouped results after aggregation. You cannot write WHERE COUNT(*) > 3 — COUNT(*) doesn't exist yet at the point WHERE runs.

SELECT channel, COUNT(*) AS num_orders
FROM orders
GROUP BY channel
HAVING COUNT(*) > 3;

Combining tables: JOIN

A JOIN lines up rows from two tables that share a common value (a "key") — here, customer_id exists in both orders and customers, so you can pull a customer's country onto every one of their orders.

orders ⋈ customers on customer_id

Conditional logic: CASE WHEN

CASE WHEN is an if/then/else you can drop inside a SELECT — the SQL version of Excel's nested IF. It checks conditions top to bottom and stops at the first match.

SELECT customer_id, revenue,
  CASE
    WHEN revenue >= 100 THEN 'High'
    WHEN revenue >= 50  THEN 'Medium'
    ELSE 'Low'
  END AS spend_tier
FROM orders;

Cleaning text: string functions

Remember the UTM-casing problem from Module 4 ("Email" vs "email" fragmenting a channel into two rows)? This is how you'd fix it in SQL rather than at the source:

FunctionDoes
UPPER(x) / LOWER(x)forces consistent case
TRIM(x)removes leading/trailing spaces
x || y (or CONCAT on some engines)joins two text values together
SELECT LOWER(TRIM(channel)) AS channel_clean FROM orders;

Working with dates

This dataset's month column ('2025-05') was itself pulled out of order_date ('2025-05-16') using a date function — in SQLite, strftime('%Y-%m', order_date). Every SQL engine has its own date-function names (BigQuery uses FORMAT_DATE), but the idea — extract a smaller unit from a full date — is universal.

Combining result sets: UNION

UNION stacks the results of two separate SELECTs into one list (and removes duplicates; UNION ALL keeps them and is faster). Rare in day-to-day marketing analysis, but shows up when combining two differently-sourced tables with the same shape — e.g. this month's data and last month's, stored separately.

SELECT channel FROM orders WHERE month = '2025-05'
UNION
SELECT channel FROM orders WHERE month = '2025-04';

Breaking a big question into steps: subqueries and CTEs

A subquery is a query nested inside another — usually because you need a computed value (like an average) before you can filter on it. A CTE (WITH name AS (...)) does the same thing but names the intermediate result, so a complex query reads top-to-bottom like numbered steps instead of nested parentheses.

a CTE is just a named, temporary step

Advanced

Window functions: the full family

A window function looks across a group of related rows without collapsing them into one row the way GROUP BY does — you still get one output row per input row, plus a calculated column. PARTITION BY defines the group (like GROUP BY, but non-collapsing); ORDER BY inside the OVER() defines the order the function walks the rows in.

RANK() OVER (PARTITION BY country ORDER BY revenue DESC)

FunctionDoes
RANK()1,2,2,4 — ties share a rank, next rank skips
DENSE_RANK()1,2,2,3 — ties share a rank, next rank doesn't skip
ROW_NUMBER()1,2,3,4 — always unique, ties broken arbitrarily
LAG(col) / LEAD(col)pulls the previous / next row's value into the current row — the standard way to compute period-over-period change
SUM(col) OVER (ORDER BY ...)running total

Cohort analysis & working with real analytics exports

  • Cohort retention: group customers by signup month, then track how many of each cohort ordered in each subsequent month.
  • Correlated subqueries: a subquery referencing the outer query's current row — powerful but can be slow on huge tables; a window function is often the faster equivalent.
  • Query performance (conceptually): an index is like a book's table of contents for a column — lets the database find rows without scanning every one. You won't build indexes as a marketing analyst, but knowing why a 50M-row query is slow (no index on the filtered column) is a real interview topic.
  • GA4's BigQuery export schema: event parameters are stored nested and repeated per event — UNNEST(event_params) flattens them into rows you can filter and aggregate on. The single biggest jump from this course's flat schema to a real GA4 SQL analysis.

Market Basket Analysis & Lift

A classic retail/e-commerce question: "which two products get bought together more often than random chance would predict?" This is what recommendation engines and store-layout decisions are built on.

Lift compares how often two products actually co-occur to how often they'd co-occur if purchases were totally independent:

Lift(A, B) = P(A and B) / (P(A) × P(B)) — Lift > 1 means the products are bought together more than chance (a real association, worth bundling/cross-selling). Lift < 1 means they're bought together less than chance (possibly substitutes for each other, not complements).

co-occurrence in this course's order_items data

Run it, then look at the two rows: Starter Kit + Pro Add-on comes back around 1.25 lift (bought together more than chance). Support Plan + Starter Kit comes back well under 1 — they're rarely bought together, despite Starter Kit being the most popular single product.

RFM Scoring with NTILE()

Module 1 and Portfolio Project 1 already used RFM (Recency, Frequency, Monetary) conceptually. Here's the real technique analysts use to turn it into a clean, comparable score: NTILE(4) splits customers into four equal-sized buckets (quartiles) by whichever column you order by — bucket 4 as "best" for all three dimensions, so a 433 customer is easy to read as "recent, but not the most frequent or highest-spending."

Interview questions for this module

"Write a query to find the top 3 campaigns by conversion rate in each region."

Model answer: use RANK() OVER (PARTITION BY region ORDER BY conversion_rate DESC) in a subquery, then filter the outer query to rank <= 3. Partitioning is the key idea — it resets the ranking within each region instead of across the whole table.

"What's the difference between INNER JOIN and LEFT JOIN, and when would a marketing analyst care?"

Model answer: INNER JOIN only keeps rows with a match in both tables; LEFT JOIN keeps every row from the left table even without a match. A LEFT JOIN matters for churn or inactivity analysis — you need customers with zero orders to show up, not disappear.

"How would you find month-over-month percent change in spend using SQL?"

Model answer: LAG(spend) OVER (PARTITION BY channel ORDER BY month) to get the prior month's value in the same row, then compute (spend - prior_spend) / prior_spend.

Real, sourced: "Given two dates, return one row per week between them, numbered sequentially." (see the Interview Bank for source)

Model answer: this is a "date spine" problem — generate a continuous sequence of dates or week numbers (a recursive CTE, or a pre-built calendar table), then join your real data onto it so weeks with zero activity still appear as a row instead of silently disappearing.

"How would you handle missing data or outliers when using SQL for marketing analysis?" (real, sourced)

Model answer: for missing values, decide explicitly between COALESCE-to-a-default, excluding the row, or flagging it — and say which. For outliers, don't silently delete: a $50,000 single order might be a real enterprise deal, not a data error. Check before excluding, and disclose it in the write-up if you do.

"How would you find products that are frequently bought together?"

Model answer: self-join an order_items-style table to itself on order_id, count co-occurrences per product pair, and compute lift against each product's independent purchase frequency — lift above 1 signals a real association worth acting on (bundling, cross-sell placement), not just popularity.
