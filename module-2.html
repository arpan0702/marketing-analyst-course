Beginner

Start here: what a database actually is

A database is just a set of spreadsheets (called tables) that can talk to each other. Each table has columns (like a spreadsheet's headers) and rows (one row = one thing — one order, one customer). SQL is the language for asking that set of tables a question. Everything below — SELECT, JOIN, GROUP BY — is one type of question.

Core concepts

  • SELECT, WHERE, ORDER BY, LIMIT — basic retrieval.
  • JOIN (INNER, LEFT) — combining an orders table with a customers table.
  • GROUP BY + aggregations (SUM, COUNT, AVG) — the pivot table, formalized.
  • Window functions (RANK(), LAG()) — rank within a group, month-over-month change.
  • CASE WHEN for segment bucketing.

Intermediate

Breaking a question into steps

  • CTEs (WITH name AS (...)): name an intermediate result so a complex query reads top-to-bottom instead of as nested parentheses. Anywhere you'd build one pivot table, then a second pivot table off the first, a CTE is that same move in SQL.
  • Subqueries: a query inside a query, often to filter against a computed value (e.g. "channels above the average revenue" — you can't write WHERE revenue > AVG(revenue) directly, the average has to be computed first).
  • HAVING vs. WHERE: WHERE filters rows before grouping; HAVING filters groups after aggregation (e.g. "channels with more than 5 orders").
  • COALESCE: COALESCE(discount, 0) substitutes a default when a value is NULL — the SQL version of Module 1's blank-handling.
  • Date functions: pulling a month or week out of a full date (SQLite: strftime('%Y-%m', order_date)) — this is how the month column in this dataset was actually derived.

Advanced

Cohort analysis & working with real analytics exports

  • Cohort retention: group customers by their signup month, then track how many of each cohort ordered in each subsequent month — the query the "improve retention" case interview question is actually asking for.
  • Correlated subqueries: a subquery that references the outer query's current row (e.g. "each customer's revenue vs. their own country's average") — powerful but can be slow on large tables; a window function is often the faster equivalent.
  • Query performance (conceptually): an index is like a book's table of contents for a column — it lets the database find matching rows without scanning every one. You won't be building indexes as a marketing analyst, but knowing why a query on a 50M-row events table is slow (no index on the filtered column) is a real interview topic.
  • GA4's BigQuery export schema: unlike this course's flat orders table, GA4's export stores event parameters as a nested, repeated field — you need UNNEST(event_params) to flatten them into rows before you can filter or aggregate on a specific parameter like campaign. This single function is the biggest jump from this course's schema to a real GA4 SQL analysis (see Module 4, Advanced).

Check your understanding

Interview questions for this module

"Write a query to find the top 3 campaigns by conversion rate in each region."

Model answer: use RANK() OVER (PARTITION BY region ORDER BY conversion_rate DESC) in a subquery, then filter the outer query to rank <= 3. Partitioning is the key idea — it resets the ranking within each region instead of across the whole table.

"What's the difference between INNER JOIN and LEFT JOIN, and when would a marketing analyst care?"

Model answer: INNER JOIN only keeps rows with a match in both tables; LEFT JOIN keeps every row from the left table even without a match. A LEFT JOIN matters for churn or inactivity analysis — you need customers with zero orders to show up, not disappear.

"How would you find month-over-month percent change in spend using SQL?"

Model answer: LAG(spend) OVER (PARTITION BY channel ORDER BY month) to get the prior month's value in the same row, then compute (spend - prior_spend) / prior_spend.

Real, sourced: "Given two dates, return one row per week between them, numbered sequentially." (see the Interview Bank for source)

Model answer: this is a "date spine" problem — generate a continuous sequence of dates or week numbers (a recursive CTE, or a pre-built calendar table), then join your real data onto it so weeks with zero activity still appear as a row instead of silently disappearing.

"How would you handle missing data or outliers when using SQL for marketing analysis?" (real, sourced)

Model answer: for missing values, decide explicitly between COALESCE-to-a-default, excluding the row, or flagging it — and say which. For outliers, don't silently delete: a $50,000 single order might be a real enterprise deal, not a data error. Check before excluding, and disclose it in the write-up if you do.
